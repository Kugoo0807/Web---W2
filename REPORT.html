REPORT — API Composition

1. Lựa chọn kỹ thuật

Nhóm dùng Node.js 22 + Express để các REST service, BFF và client cùng dùng JavaScript; khởi động nhanh, phù hợp thời lượng thực hành. Spring Boot không được chọn vì cấu hình và vòng lặp build lớn hơn trong khi không phục vụ trực tiếp mục tiêu so sánh API composition.

Mỗi service sở hữu một file SQLite riêng. Cách này dễ nạp dữ liệu và chạy lại trên localhost; kết quả không đại diện cho database phân tán hoặc tải đồng thời cao.

GraphQL dùng graphql và DataLoader. Mode n1 gọi Product Service theo từng item; mode dataloader gom ID, khử trùng lặp và gọi batch một lần. Apollo Server không cần thiết cho schema/resolver nhỏ của bài.

2. Documentation và logging

Nhóm không thêm Swagger/OpenAPI vì contract API nhỏ đã có trong README và PLAN. Nếu mở rộng hệ thống, REST API nên có OpenAPI. Nhóm cũng không dựng ELK do đây là demo localhost; telemetry service call, DB query và duration được trả về để benchmark. Production nên dùng structured logging và hệ thống quan sát tập trung.

3. Policy lỗi

BFF và GraphQL cùng dùng partial failure: khi Product Service lỗi hoặc timeout 1500 ms, User/Order vẫn trả về, product là null, response có errors, và không thay thế bằng dữ liệu giả.

4. Đo lường và giới hạn

  • Payload là số byte UTF-8 của JSON response body, không gồm HTTP header/request body.
  • Cold run là lần đầu sau khi restart các service cho biến thể đó; bốn lần kế là warm run.
  • Kết quả localhost dao động theo máy và tiến trình nền; chỉ so sánh cùng dữ liệu, query fields và môi trường.

Xem số đo raw trong BENCHMARK_REPORT.md và trace/lỗi trong EVIDENCE.md.

5. Trade-off

Baseline đơn giản ở server nhưng khiến client chatty. BFF trả response phù hợp từng client nhưng tăng endpoint cần duy trì. GraphQL linh hoạt về field, đổi lại phải batch/dedup để tránh N+1 và cần kiểm soát query khi mở rộng.
